# Trajectory Pipeline: Raw JSON to VLM Training Data

This document explains the end-to-end pipeline for converting a raw trajectory JSON (generated by an LLM planner) into a fully rendered trajectory with images and videos that can be used to train a vision-language model (VLM).

## Pipeline Overview

```
Raw Trajectory JSON (symbolic IDs)
        |
        v
  TrajectoryAdapter.adapt()
        |  - resolves symbolic IDs to concrete sim IDs
        |  - resolves initial state (objects, fixtures, agents)
        |  - normalizes step format
        v
  Adapted Trajectory JSON (concrete IDs)
        |
        v
  SimToolExecutor.load_initial_state()
        |  - opens/closes fixture parts
        |  - moves objects to starting positions
        |  - robots stay at sim-assigned spawn
        v
  SimToolExecutor.run_tool_plan()
        |  - executes each step sequentially
        |  - renders before/after frames per camera per step
        |  - writes per-camera MP4 videos
        |  - records execution metadata with image paths
        v
  Output Directory (ready for VLM training)
```

## Input: Raw Trajectory JSON

A raw trajectory JSON is produced by an LLM planner. It uses symbolic IDs (not concrete sim IDs) and contains:

- `trajectory_id`: unique identifier
- `composite_task`: task class name (e.g. `HotDogSetup`)
- `agents`: list of agent definitions
- `initial_state`: object types, fixture types, agent locations (all symbolic)
- `grounding_map`: (optional, legacy) type hints for resolution
- `steps`: ordered tool calls with symbolic IDs in args
- `validation`: planner's self-check of trajectory validity

Example symbolic IDs in a raw trajectory:
- Objects: `bun`, `sausage`, `serving_plate`
- Fixtures: `bun_source_fixture`, `sausage_source_fixture`, `serving_surface`

These must be resolved to concrete sim IDs like `hotdog_bun`, `counter_1_right_group_1`, etc.

## Running the Pipeline

```bash
python -m robocasa.utils.sim_tool_executor \
  --task HotDogSetup \
  --trajectory path/to/raw_trajectory.json \
  --robots 2 \
  --layout 11 \
  --style 42 \
  --seed 42 \
  --placement grid \
  --output-dir tmp/output
```

The `--task`, `--layout`, `--style`, and `--seed` flags create the concrete kitchen instance. The trajectory's symbolic IDs are resolved against this specific scene.

## Output Files

### `adapted_trajectory.json`

The trajectory with all symbolic IDs resolved to concrete sim IDs. Contains:

- `trajectory_id`, `composite_task`: carried from input
- `initial_state`: resolved — concrete object IDs, fixture IDs, agent locations
- `tool_calls`: the executable plan with concrete IDs in all args
- `resolution_log`: audit trail showing how each symbolic ID was resolved (method, confidence, reason)
- `source_trajectory`: the original raw trajectory for reference

**Purpose**: This is the grounded plan. It shows exactly what the executor will run. The resolution log makes it auditable — you can verify that every symbolic ID was mapped correctly.

### `trajectory_execution_metadata.json`

The execution results with per-step image paths. Contains:

- `trajectory_id`, `composite_task`
- `load_initial_state`: summary of what was loaded (agents, objects, fixtures, held objects)
- `resolution_log`: same as adapted trajectory
- `task`: natural language task description
- `steps`: per-step execution results, each with:
  - `step_index`, `tool`, `robot_idx`, `args`
  - `success`: whether the step succeeded
  - `details`: executor return details
  - `robot_positions`: XYZ positions of all robots after the step
  - `image_paths`: per-camera before/after frame paths for this step
- `cameras`: list of available camera names

**Purpose**: This is the primary artifact for VLM training data construction. Each step has `image_paths` mapping camera names to before/after PNG paths. A data loader can pair the step's tool call + reasoning with the corresponding images.

### `plan.json`

The grounded tool call list that was actually executed (after template resolution). Same content as `adapted_trajectory.tool_calls` but as a standalone file.

**Purpose**: Quick reference for what was executed, without the full adapted trajectory wrapper.

### `metadata.json`

Same content as `trajectory_execution_metadata.json` but written by `run_tool_plan` directly (before the adapter merges in resolution metadata).

**Purpose**: Lower-level execution log. The `trajectory_execution_metadata.json` is the preferred file since it includes the resolution log.

### `initial_map.png`

The 2D placement map showing fixture footprints, object positions, and robot positions at scene initialization (before any trajectory steps).

**Purpose**: Visual debugging of the scene layout. Useful for verifying that objects and robots are in expected positions before execution begins.

### `frames/`

Directory of per-camera frame PNGs organized as:

```
frames/
  room_view/
    initial.png
    step_000_before.png
    step_000_after.png
    step_001_before.png
    step_001_after.png
    ...
  top_view/
    initial.png
    step_000_before.png
    ...
  robot0_agentview_center/
    ...
  robot0_eye_in_hand/
    ...
  robot1_agentview_center/
    ...
```

Each step produces a before and after frame from every camera. The `initial.png` captures the scene after `load_initial_state` but before any tool steps.

**Purpose**: The raw image data for VLM training. Each frame can be paired with the corresponding step's tool call, reasoning, and success status from the execution metadata.

### `*.mp4` (per-camera videos)

One MP4 video per camera, showing the full trajectory as a sequence of before/after frames.

- `room_view.mp4` — wide scene view
- `top_view.mp4` — overhead view
- `robot0_agentview_center.mp4` — robot 0's center camera
- `robot0_eye_in_hand.mp4` — robot 0's wrist camera
- `robot1_agentview_center.mp4` — robot 1's center camera
- etc.

**Purpose**: Quick visual review of the full trajectory. Useful for debugging and quality assessment before using the data for training.

## VLM Training Data Construction

To build training data from the pipeline output:

1. Load `trajectory_execution_metadata.json`
2. For each step, extract:
   - **Input image**: `step.image_paths[camera_name].before` — the scene before the action
   - **Action**: `step.tool` + `step.args` — the tool call that was executed
   - **Reasoning**: from the adapted trajectory's `tool_calls[step_index].metadata.reasoning`
   - **Output image**: `step.image_paths[camera_name].after` — the scene after the action
   - **Success**: `step.success` — whether the action succeeded
   - **Robot positions**: `step.robot_positions` — spatial context
3. Filter by `success == true` to exclude failed steps
4. Choose cameras based on training requirements (e.g. `room_view` for global context, `eye_in_hand` for manipulation detail)

## ID Resolution

Symbolic IDs are resolved using sim ground truth (confidence 1.0) by tracing through:

- `env.objects` keys (from task's `_get_obj_cfgs()`), first by exact symbol match, then by exact `object_type`-as-id match, then by generic type match
- `env.object_cfgs` placement fixtures
- `env.fixture_refs` (from task's `_setup_kitchen_references()`)

See [trajectory_resolution_and_workflow.md](./trajectory_resolution_and_workflow.md) for details.

## Known Limitations

- **Fixture articulation**: The executor does not auto-open fridges/cabinets before picking objects inside them. Trajectories must include explicit `open_hinged_part` steps. If the LLM planner omits these, the trajectory will execute but the door stays closed. This needs a solution (auto-open on pick, or planner enforcement).
- **Fridge doors**: Same issue — the fridge door is never opened in current trajectories because the LLM planner doesn't generate the open step.
- **Navigation failures**: `pick_up_object` now correctly returns failure when the robot can't reach the source fixture. Failed steps should be filtered from training data.
- **Teleport-based**: Robot motion is instantaneous (teleport), not physically realistic. This is acceptable for symbolic trajectory data but means the images don't show realistic motion.
