# Trajectory Pipeline: Raw JSON to VLM Training Data

This document explains the end-to-end pipeline for converting a raw trajectory JSON (generated by an LLM planner) into a fully rendered trajectory with images that can be used to train a vision-language model (VLM).

## Pipeline Overview

```
Raw Trajectory JSON (symbolic IDs, with get_image steps)
        |
        v
  TrajectoryAdapter.adapt()
        |  - resolves symbolic IDs to concrete sim IDs
        |  - resolves initial state (objects, fixtures, agents)
        |  - resolves get_image paths relative to output dir
        |  - normalizes step format
        v
  Adapted Trajectory JSON (concrete IDs)
        |
        v
  SimToolExecutor.load_initial_state()
        |  - opens/closes fixture parts
        |  - moves objects to starting positions
        |  - robots stay at sim-assigned spawn
        v
  SimToolExecutor.run_tool_plan()
        |  - executes each step sequentially
        |  - get_image steps render and save to their specified paths
        |  - records execution metadata
        v
  Output Directory (ready for VLM training)
```

## Input: Raw Trajectory JSON

A raw trajectory JSON is produced by an LLM planner. It uses symbolic IDs (not concrete sim IDs) and contains:

- `trajectory_id`: unique identifier
- `composite_task`: task class name (e.g. `HotDogSetup`)
- `agents`: list of agent definitions
- `initial_state`: object types, fixture types, agent locations (all symbolic)
- `grounding_map`: (optional, legacy) type hints for resolution
- `steps`: ordered tool calls with symbolic IDs in args, interleaved with `get_image` steps
- `validation`: planner's self-check of trajectory validity

The trajectory interleaves action steps and `get_image` steps. Each `get_image` step specifies which camera views to render and where to save them:

```json
{
  "tool": "get_image",
  "args": { "views": ["wrist", "agentview_center"] },
  "image_paths": [
    "images/traj_000000/3_wrist_agent_0.png",
    "images/traj_000000/3_agentview_center_agent_0.png"
  ]
}
```

## Running the Pipeline

Single trajectory:

```bash
python -m robocasa.utils.sim_tool_executor \
  --trajectory path/to/raw_trajectory.json \
  --robots 2 \
  --layout 11 \
  --style 34 \
  --seed 42 \
  --placement grid \
  --output-dir tmp/output
```

Sweep all trajectories in a dataset:

```bash
python scripts/sweep_trajectories.py \
  --input-dir data_generation/task_level/data/image/20260324T031125Z \
  --output-dir tmp/sweep_output
```

The `--layout`, `--style`, and `--seed` flags create the concrete kitchen instance. The trajectory's symbolic IDs are resolved against this specific scene. If not specified, defaults are layout=11, style=34, seed=42.

## Output Files

### `adapted_trajectory.json`

The trajectory with all symbolic IDs resolved to concrete sim IDs. Contains:

- `trajectory_id`, `composite_task`: carried from input
- `initial_state`: resolved — concrete object IDs, fixture IDs, agent locations
- `tool_calls`: the executable plan with concrete IDs in all args, including resolved `get_image` paths
- `resolution_log`: audit trail showing how each symbolic ID was resolved (method, confidence, reason)
- `source_trajectory`: the original raw trajectory for reference

**Purpose**: The grounded plan. The resolution log makes it auditable — you can verify that every symbolic ID was mapped correctly.

### `trajectory_execution_metadata.json`

The execution results. Contains:

- `trajectory_id`, `composite_task`
- `load_initial_state`: summary of what was loaded (agents, objects, fixtures, held objects)
- `resolution_log`: same as adapted trajectory
- `task`: natural language task description
- `steps`: per-step execution results, each with:
  - `step_index`, `tool`, `robot_idx`, `args`
  - `success`: whether the step succeeded
  - `details`: executor return details
  - `robot_positions`: XYZ positions of all robots after the step
  - `image_paths`: (on `get_image` steps) list of saved image file paths
- `cameras`: list of available camera names

**Purpose**: Primary artifact for VLM training data construction. Pair each action step with the images from its surrounding `get_image` steps.

### `plan.json`

The grounded tool call list that was actually executed. Same content as `adapted_trajectory.tool_calls` but as a standalone file.

### `metadata.json`

Same content as `trajectory_execution_metadata.json` but without the resolution log.

### `images/`

Images rendered by `get_image` tool calls, saved to the paths specified in the trajectory:

```
images/traj_000000/
  0_top_view_agent_0.png
  0_room_view_agent_0.png
  0_map_agent_0.png
  3_wrist_agent_0.png
  3_agentview_center_agent_0.png
  5_wrist_agent_0.png
  5_agentview_center_agent_0.png
  ...
```

The naming convention is `{step_index}_{view}_{agent}.png`. Images are only rendered when the trajectory includes `get_image` steps — there is no bulk frame dump.

**Purpose**: The image data for VLM training. Each image corresponds to a specific `get_image` step in the trajectory, rendered from the agent's perspective at that point in execution.

## VLM Training Data Construction

To build training data from the pipeline output:

1. Load `trajectory_execution_metadata.json`
2. Walk through steps in order. `get_image` steps produce images; action steps produce state changes.
3. For each action step, pair it with:
   - **Before images**: from the preceding `get_image` step
   - **After images**: from the following `get_image` step
   - **Action**: `step.tool` + `step.args`
   - **Reasoning**: from `adapted_trajectory.tool_calls[step_index].metadata.reasoning`
   - **Success**: `step.success`
4. Filter by `success == true` to exclude failed steps

## ID Resolution

Symbolic IDs are resolved using sim ground truth (confidence 1.0) by tracing through:

- `env.objects` keys (from task's `_get_obj_cfgs()`), first by exact symbol match, then by exact `object_type`-as-id match, then by generic type match
- `env.object_cfgs` placement fixtures
- `env.fixture_refs` (from task's `_setup_kitchen_references()`)

See [trajectory_resolution_and_workflow.md](./trajectory_resolution_and_workflow.md) for details.

## Known Limitations

- **Fixture articulation**: The executor does not auto-open fridges/cabinets before picking objects inside them. Trajectories must include explicit `open_hinged_part` steps. If the LLM planner omits these, the trajectory will execute but the door stays closed.
- **Navigation failures**: `pick_up_object` returns failure when the robot can't reach the source fixture. Failed steps should be filtered from training data.
- **Teleport-based**: Robot motion is instantaneous (teleport), not physically realistic. This is acceptable for symbolic trajectory data but means the images don't show realistic motion.
